# AI 电商运营助手 —— 完整想法描述与执行框架

> 项目定位：**求职作品集**。核心不是做商业产品，而是证明：能把多模态模型应用到真实业务、能用 LLM 解决真实电商问题、能设计 AI 工作流与统一模型接口、理解电商运营流程与平台规则、理解 AI 能力边界。

---

## 一、一句话概括

用户上传一张商品图片（可选补充说明），系统用多模态大模型"看懂"商品可见属性 → 组织成结构化商品信息 → 按淘宝/京东/小红书分版生成标题、卖点、详情页、短视频脚本、AI 营销图 Prompt → 汇总成一份可导出的《AI 电商商品运营报告》。

## 二、目标

| 目标 | 说明 |
|---|---|
| G1 业务目标 | 一键把"一张图"变成"一套可执行的电商运营方案"，覆盖商品理解 → 定位 → 文案 → 素材方案全流程 |
| G2 展示目标 | 评委/HR **无 API key、无耐心**也能 30 秒内完整看完流程：内置 Mock 示例 + 分步进度 + 秒开缓存 |
| G3 技术目标 | 展示多模态识别、LLM 工作流编排、JSON Schema 强约束输出、统一模型接口（可插拔供应商）、CV 抠图（独立展示链路）、SQLite 缓存、前后端分离 |

## 三、设计原则（技术边界的前置约束）

1. **演示优先**：Mock 示例模式 + 分步进度反馈 + 结果缓存是硬需求。
2. **不编造模型看不出的东西**：材质/品牌/价格/竞争优势等不可见属性，单图推不准，**必须由用户文本输入提供**；视觉模型只推断"可见属性"，每个字段标注来源（visual / user）并在前端明示。
3. **深度优于广度**：第一版只做少量功能，做到无可挑剔。
4. **分析用原图，抠图只做展示**：视觉分析（LLM 链路）与主体抠图（CV 链路）**两条独立链路**，抠图结果不进分析，避免 CV 误差污染 LLM 判断。

## 四、主要功能模块

### F1 商品图片上传模块
网页上传（拖拽/选择），支持 jpg/png/webp，类型白名单 + 大小限制 + 文件名清洗；可选填商品名称与补充说明（提供材质/品牌等事实信息）。

### F2 商品主体提取模块（展示链路）
`rembg`（预留 SAM/U²-Net 接口），输出透明背景 PNG，仅用于报告中"商品主体识别"视觉对照；**模型/服务不可用时自动降级为原图**，不影响演示。

### F3 商品视觉理解模块（核心，分析链路）
将**原图 + 可选文本**发给多模态模型，输出 **JSON Schema 强约束**结构化字段：
- 视觉推断（visual）：商品类别、外观特点、风格、使用场景
- 事实输入（user）：从用户文本提取的材质、品牌、价格、竞争优势

### F4 用户画像生成模块
按商品信息生成画像卡：年龄、职业、消费能力、购买场景、动机、痛点。

### F5 运营内容生成模块（核心，按平台分版 = 运营专业性体现）
- 电商标题：淘宝版（60 字关键词堆叠）/ 京东版（专业）/ 小红书版（种草）
- 五点卖点：每条含标题 + 解释
- 详情页：痛点 → 方案 → 核心功能 → 场景 → 购买理由
- 短视频脚本：钩子前三秒 → 分镜 → 旁白 → 展示 → 转化结尾

### F6 AI 营销图片方案
第一版只生成"场景化 AI 图片 Prompt"（含正/负向提示词、比例、构图说明），不真实出图；未来可接 SD/即梦/可灵。

### F7（推迟）运营建议
不做"数据分析 Agent"（无真实数据即是空壳）；若做仅基于平台规则知识库给规则化建议。

## 五、目标用户与使用场景

| 维度 | 描述 |
|---|---|
| 目标用户 | ① 作品集评委/HR（只看演示，无 key）；② 中小电商运营/个体卖家（有 key，传自己商品图）；③ 需要批量起标题/写详情/写脚本的运营（复用缓存，同图秒出） |
| 典型场景 A | 演示场景：一键加载"保温杯/咖啡杯/耳机"示例 → 逐步动画 → 全报告，无 API key |
| 典型场景 B | 真实场景：卖家传自家商品图 + 填"304 不锈钢/¥129/自有品牌" → 获得可落地三平台文案 |
| 典型场景 C | 二次复用：同图再次上传 → 命中缓存，秒开历史报告 |

## 六、数据来源（明确的数据边界）

| 数据 | 来源 | 可靠性 |
|---|---|---|
| 商品可见属性（类别/外观/风格/场景） | 视觉模型分析原图 | 中（模型能力内） |
| 材质/品牌/价格/竞争优势 | **用户文本输入** | 高（事实输入） |
| 平台规则知识（60 字/关键词堆叠等） | 写死在 Prompt 模板知识段 | 高（规则静态） |
| 运营数据/销量数据 | **无** → 明确不做数据分析 | —（防止空壳） |

## 七、期望的自动化程度

| 环节 | 自动化程度 |
|---|---|
| 图片上传 → 任务创建 | 全自动 |
| 视觉分析 / 抠图 / 文案生成 | 全自动（后台任务流水线） |
| 供应商选择 | 自动：检测到有效 API key → 走真实模型；否则 → Mock 引擎（可前端手动强制 Mock） |
| 结果复用 | 自动缓存：图片 hash 命中即秒开 |
| 用户必须参与点 | 仅"补充事实信息"（可选）与"最终人工审核发布"——这正是 AI 能力边界的正确切分 |

## 八、技术架构与模块边界

```
单仓库 monorepo
├── frontend    React + TypeScript + Vite（上传页 / 进度页 / 报告页）
├── backend     Python FastAPI
│   ├── providers/      统一模型接口：Base(结构化JSON) → Mock / OpenAI兼容
│   ├── vision/         视觉理解（多模态，含 json schema）
│   ├── llm/            文本生成（标题/卖点/详情/脚本/画像）
│   ├── segmentation/   抠图 rembg（可降级）
│   ├── prompts/        所有 Prompt 模板（.txt，占位符渲染）
│   ├── services/       业务编排：分析 → 生成 → 汇总；后台任务 + 进度
│   └── db/             SQLite（任务 + 报告缓存）
├── examples/images     示例商品图 + 预生成 Mock 报告 JSON
└── uploads|outputs     运行时产物
```

- 结构化输出：所有生成调用统一走 `chat_json(messages, schema)` → 后端 pydantic 二次校验 → 失败重试 → 降级宽松解析。
- 视觉请求：`data URL` 内嵌原图 + `response_format=json_object`（OpenAI 兼容协议，便于换 GLM/Qwen 等国内端点）。
- 前端轮询 `/api/tasks/{id}` 获取分步进度（步骤含状态与文案）。

## 九、开发优先级（落地顺序 = 依赖顺序）

1. **P0 打通演示闭环**：上传 + 校验 + Mock 引擎 + 进度反馈 + 报告页 + 导出 —— 无 key 可完整跑通（对应上文 G2）
2. **P0 真实模型链路**：OpenAI 兼容适配器接入视觉 + 文本（对应 G3"统一模型接口"）
3. **P0 缓存**：图片 hash → SQLite 报告缓存（对应场景 C）
4. **P1 抠图展示链路**：rembg + 降级（分析/展示解耦的架构演示点）
5. **P1 三平台分版文案 + 画像 + 脚本 + 营销图 Prompt 内容打磨**
6. **P2（可选）** 运营建议知识库、真实出图对接

## 十二、技术边界与风险控制

- **不做**：销量数据分析、通用 RAG、材质/价格自动推断、真实出图 —— 均已在设计中显式声明为"不做"。
- **降级链**：模型调用失败 → 重试 1 次 → Mock 结果并标注；抠图失败 → 原图；解析失败 → 宽松字段兜底。
- **演示可靠性**：视觉分析真实调用只发生在"有 key 且非强制 Mock"时，演示环境永远有 Mock 兜底，**绝不卡死**。

## 十三、优化建议（后续演进，均有真实价值）

1. 报告 → PDF 排版导出、多报告对比视图。
2. 平台规则升级为"版本化知识库"（淘宝改版时只改规则不改成套 Prompt）。
3. 抠图升级 SAM2 提升边缘质量（接口已预留）。
4. 接真实出图（SD/即梦/可灵），把"Prompt 方案"变成"素材生成"。
5. 批量模式：一次多图，表格化产出（服务编排已支持复用）。
6. 加入图像 hash 去重与报告版本管理。
